# Production hardening by evidence

Use this review before first users, first payment, or a material change to a live app. Keep the [web-to-mobile playbook](WEB_TO_MOBILE_LAUNCH_PLAYBOOK.md) as the release sequence and the existing launch tracker as the status authority. This guide decides which risks need action; a checklist is not a security certification.

SaaS-Viber itself is documentation scaffolding: no `src/` application and empty dependency sections at the reviewed baseline. React/TypeScript/Vite/Tailwind conventions and Supabase/Stripe examples are adoption choices, not installed services. Do not claim build, RLS, payment or device tests passed on this template.

## Review packet and decision rules

1. Verify repository, remote, branch/commit, deployment target, native client/server mapping, current owner and dirty worktrees. Read contracts, existing skills, release tracker and open fixes. Preserve ongoing jobs; coordinate with their owner before app edits.
2. Inventory actual data flows: local vs remote storage, public vs private data, authentication, uploads, payments, AI calls, scheduled jobs and external processors. Mark absent capabilities not applicable with a reason.
3. Record each finding in the existing tracker using the [evidence template](../templates/HARDENING_REVIEW_TEMPLATE.md). Classify separately: **verified defect**, **untested risk**, **not applicable**, **post-traction improvement**, or **verified control**. Cite dated code/test/provider evidence and its environment. Source code is not proof of deployed configuration.
4. Prioritize by impact and exposure. **P0:** demonstrated unauthorized access, corruption or duplicate financial effects; investigate urgently without a speculative production patch. **P1:** applicable core-flow or recovery risk before the affected release. **P2:** worthwhile usability/operational improvement. **P3:** measured scale/team need. An unknown is not a confirmed vulnerability or a pass.
5. Propose the smallest fix, specific positive and negative tests, regression risk, rollback/recovery and release dependency. Separate implementation-ready work from product/legal/provider decisions. Obtain the required merge/release approval on the concrete reviewed diff.

For live changes, retain the deployed version and recovery instructions, test synthetic fixtures in an isolated environment, use a bounded rollout and define a stop signal. Do not change production policies, permissions, credentials, billing settings or real-user data as an audit shortcut. Never merge/deploy from a checklist. Do not deliberately break production to prove an alert. Keep private app/account details out of public template PRs.

## Applicable first-user and first-payment checks

| Area | Minimal evidence and test | Gate only when applicable |
|---|---|---|
| UI and accessibility | Core task loading/empty/error/success, failed-input preservation, keyboard/focus, text zoom and narrow-screen tests; offline/interruption/restart on native | Inability to complete or recover a core task blocks that flow. Animation, universal skeletons, token purity and arbitrary Lighthouse scores are not blanket blockers. Use existing design system; assess accessibility requirements explicitly. |
| Secrets and configuration | Inspect public env definitions and built artifacts; use approved secret scanning with redacted output, including relevant history | Vite public variables are client-visible; public identifiers are not private keys. An actual leak needs an owner-coordinated incident/rotation plan. Never print secret values or automatically rotate. [Vite](https://vite.dev/guide/env-and-mode) |
| Auth and authorization | Synthetic signed-out, owner, other-user and role tests on each protected operation; reset reuse/expiry, session revocation, Unicode and email aliases | Check resource authorization at the trusted boundary, including privileged server paths; UI hiding is insufficient. Explicitly public endpoints need input/abuse checks, not mandatory login. |
| Database exposure | Inventory exposed schemas, grants, views, functions, service-role paths and policies; deny cross-tenant reads/writes with two synthetic identities | For Supabase exposed tables, review RLS **and** privileges. Do not blindly enable RLS on every internal table or infer safety from policy existence. Service roles can bypass policies. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) |
| Storage and uploads | Test bucket visibility and per-operation object access separately; bounded byte count, actual format, safe names, content delivery and cleanup | Buckets are not ordinary application tables. Review `storage.objects` policies, public reads, signed URLs and upload/overwrite/delete separately. [Storage access](https://supabase.com/docs/guides/storage/security/access-control) |
| Input/browser boundary | Server validation, parameterized queries, output encoding, applicable CSRF defenses; test header/CORS changes against auth, embeds and native clients | CORS is not authorization. Restrictive CSP may break working clients: stage and inspect violations before enforcement. Sanitization alone does not establish XSS safety. |
| Abuse and AI spend | Bound input/output sizes, concurrency, retries and per-user/global budgets; test rejected requests and reservation/refund failures without paid model calls | Identify which provider controls are alerts vs enforceable caps. Treat model output and retrieved content as untrusted; validate tool actions and minimize sensitive data. Prompt text alone cannot prevent injection. |
| Dependencies | Verify package provenance and lockfile; triage advisory reachability and runtime vs development exposure; test scoped upgrades | A clean audit is not proof, and an advisory count is not an exploit count. Avoid forced upgrades, global overrides or adding services solely to satisfy a checkbox. |
| Billing | Sandbox raw-body signature failures, duplicate/concurrent/out-of-order events, retry after failure, checkout replay, cancellation/expiry, failed renewal, refund/dispute and plan changes | Couple durable deduplication to successful effects; do not mark an event done before work commits. Reconcile canonical provider state. Use appropriate minor units/currency rules. Native purchase/restore and server entitlements need platform-specific proof. [Stripe webhooks](https://docs.stripe.com/webhooks) |
| Data correctness | Explicit bounds/pagination with deterministic order; test beyond one page, concurrent writes and constraint failures | Avoid silently incomplete exports. Add indexes from actual query plans/workload, including write cost, rather than indexing every filtered column. |
| Time | Define instant, calendar date, local wall time and recurrence separately; test DST gaps/folds, timezone changes and travel | PostgreSQL `timestamptz` represents an instant, not the original IANA zone. Recurrence usually needs local schedule plus zone and an ambiguity policy; birthdays/all-day dates are not UTC instants. [PostgreSQL](https://www.postgresql.org/docs/current/datatype-datetime.html) |
| Deletion/export | Synthetic round-trip export/import and deletion across caches, local drafts, remote objects and retained copies | Choose retention/anonymization/hard deletion by domain and obligations. Soft deletion is not universal and can retain sensitive data. Explain backups and copies outside app control. |
| Recovery/migrations | Versioned migration and compatibility plan; restore synthetic backup to isolated target, verify integrity and elapsed recovery time | Define acceptable data loss and recovery time. Roll-forward or restore may be safer than destructive down migrations. Check object files separately from database backups; no paid tier mandated. |
| Operations/email | Sanitized error context, actionable alerts and an owner; synthetic alert route test; auth-email delivery/bounce handling when email is used | Do not log tokens, full payloads or unnecessary identifiers. Reuse existing monitoring. Verify relevant sender authentication without changing live DNS during audit. |
| Policy/ownership | Accurate product data-flow disclosures, support route and actual account/recovery ownership | Tax, consent, business structure and legal requirements depend on jurisdiction/product. Obtain owner/professional determination; do not force Stripe Tax, company conversion or paid services. |

## After traction

Add queues, distributed coordination, pooling, sophisticated observability, feature flags, infrastructure-as-code and load tests when workload, failure evidence or team size justifies them. Safe load tests use synthetic data and an approved isolated target/budget. A single local-first app does not need a backend just to satisfy this list.

## Lightweight validation

Run existing `python3 scripts/check-docs.py` and `bash scripts/check-platform-independence.sh` for template edits. Adopted apps retain their own meaningful tests and release gates. Optionally run `python3 scripts/check-hardening-review.py review.json` on a JSON review record described in the template. It checks record completeness and unresolved P0/P1 gates, **not** whether evidence is true or production is safe. It uses only the local JSON file, without network, credentials, dependency installation or application writes.

Official references checked 2026-10-19. Recheck them for the actual provider/version at adoption. Review scope and excluded systems should be stated explicitly; do not assume unreviewed controls are implemented.
